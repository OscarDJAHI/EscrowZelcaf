01 — Le contexte escrow

La preuve est le pivot de la confiance

Dans un séquestre (escrow) B2B transfrontalier, un tiers de confiance bloque les fonds de l'acheteur jusqu'à ce que le vendeur ait tenu sa part. Quand les deux parties sont en désaccord — marchandise abîmée, non livrée, non conforme — c'est un arbitre qui tranche. Et un arbitre ne tranche bien que sur des preuves.

La plateforme existante gérait déjà l'argent (une machine à états INITIATED → FUNDS_LOCKED → SHIPPED → RELEASED, branches DISPUTED → RELEASED/REFUNDED) mais aucune table de pièces jointes. Cette fonctionnalité comble ce vide : attacher des photos et documents à une transaction, et faire de la présence d'au moins une preuve la condition d'ouverture d'un litige.

📦 Vendeur

⚖️ Arbitre

🚚 Livreur

Pousser une preuve horodatée de l'état de la marchandise, via API signée (HMAC).

Principe du contradictoire — comme au procès, toutes les parties voient toutes les pièces. C'est ce qui rend l'arbitrage équitable, et c'est un invariant de visibilité que l'architecture doit garantir (AD-3).

02 — Le paradigme

Ratifier l'existant, ajouter un seul port

C'est un projet brownfield : le backend Spring Boot et le frontend Vue existent. La règle d'or de l'architecture n'est pas d'inventer, mais de ratifier les conventions déjà là et de ne créer un invariant que là où deux développeurs pourraient diverger.

Le backend suit une architecture en couches (domain → repository → service → web). La seule nouveauté structurelle est un port hexagonal : l'interface EvidenceStorage, qui isole le stockage binaire du reste. Les endpoints ne connaissent qu'une clé opaque, jamais MinIO — ce qui rend une future bascule vers un autre stockage S3 quasi gratuite.

Pourquoi un port ? Le PRD disait « disque local (POC) », la tech-stack disait « S3/MinIO ». Plutôt que de trancher pour toujours, on isole le choix derrière une interface. La décision du jour (MinIO) peut changer sans toucher une seule ligne des controllers.

03 — Le cœur durable

Onze décisions qu'un développeur ne pourrait pas deviner

Une décision d'architecture (AD) fixe ce que du code déjà conforme ne révélerait pas. Chacune porte trois choses : ce qu'elle lie, la divergence qu'elle empêche, et la règle à suivre. Les cuivrées sont imposées par le code existant ; les indigo ont été tranchées en coaching.

AD-1

Ouverture de litige composite et atomique

coaché
Empêche
un litige DISPUTED sans aucune preuve ; un rejeu offline scindé en deux entrées désynchronisables.
Règle
Un seul endpoint POST /escrow/{id}/dispute (multipart files[] 1..N + comment) ouvre le litige et attache la preuve dans une seule transaction.
Lie
FR-6, FR-15
AD-2

Fenêtre de dépôt fondée sur l'état, pas sur l'événement

adopté
Empêche
un dépôt sur une transaction figée financièrement ; deux endpoints aux règles divergentes.
Règle
Dépôt/retrait autorisés ssi state ∈ {FUNDS_LOCKED, SHIPPED, DISPUTED}. Verrou dès l'état terminal — peu importe l'événement qui y a mené.
Lie
FR-1, FR-7, FR-8
AD-3

Un contrôle d'appartenance unique (anti-IDOR)

adopté
Empêche
la référence directe d'objet non contrôlée — télécharger la pièce d'une transaction dont on n'est pas partie.
Règle
Tous les endpoints réutilisent le même contrôle « X est-il partie de Y ? ». Le téléchargement vérifie en plus que {eid}.transaction_id == {id} de l'URL.
Lie
FR-1, FR-5, FR-7, FR-9, FR-11, FR-12
AD-4

Retrait logique uniquement, avec plancher

adopté
Empêche
la perte d'une preuve ; un litige « vidé » de ses pièces ; le retrait de la pièce d'un tiers.
Règle
Aucune suppression physique (ACTIVE → WITHDRAWN). En DISPUTED, un retrait est refusé s'il amène le total de pièces actives toutes parties confondues sous 1.
Lie
FR-12, FR-13, FR-14, NFR-3
AD-5

Audit dans la même transaction

adopté
Empêche
la divergence du schéma d'audit ; une écriture d'audit hors de la transaction métier.
Règle
Chaque dépôt/retrait écrit dans audit_logs en propagation MANDATORY (commit atomique). Le payload JSONB porte l'action — pas de nouvelle colonne.
Lie
FR-13, NFR-3
AD-6

Stockage binaire derrière un port à clé opaque

adopté
Empêche
le couplage des controllers au backend de stockage ; une migration impossible sans casser l'API.
Règle
Tout passe par l'interface EvidenceStorage. Clé opaque {tx}/{uuid}, jamais dérivée du nom fourni. Seul l'adaptateur connaît MinIO.
Lie
NFR-1
AD-7

Validation serveur stricte à l'ingestion

coaché
Empêche
un type mensongé (extension/Content-Type) ; le path traversal ; le XSS stocké ; un fichier vide/oversize.
Règle
Content-sniffing du MIME réel (Apache Tika) confronté à l'extension ; taille 0 < s ≤ 10 Mo arbitrée par le service ; restitution en Content-Disposition: attachment, jamais inline.
Lie
FR-3, FR-4, NFR-2
AD-8

HMAC partenaire durci : clé dédiée + anti-rejeu

coaché
Empêche
le rejeu d'une requête interceptée ; la réutilisation du secret webhook sortant ; un dépôt sur une transaction tierce.
Règle
Signature couvrant corps+timestamp, clé dédiée entrante. Anti-rejeu figé : fenêtre ±5 min, nonce unique par key-id, rétention ≥ fenêtre.
Lie
FR-5, NFR-5
AD-9

Hors-ligne : une entrée de file portant le binaire

coaché
Empêche
le dépassement du quota localStorage ; une ouverture de litige offline scindée ; la perte silencieuse d'un fichier.
Règle
La file offline migre vers IndexedDB pour porter des Blob (≤10 Mo). Une ouverture offline = une seule entrée, rejouée en multipart vers l'endpoint composite.
Lie
FR-15, NFR-4
AD-10

Synchro : réconciliation transitoire vs permanent

coaché
Empêche
une boucle de retry infinie ; un état optimiste mensonger ; la perte silencieuse d'un fichier en attente.
Règle
Classer l'échec par code applicatif, pas par classe HTTP. Transitoire (réseau, 5xx, 409-lock) ⇒ re-tenter ; permanent (énuméré) ⇒ annuler l'optimiste, garder le binaire, notifier, stopper.
Lie
FR-16
AD-11

Horodatage : serveur source de vérité

coaché
Empêche
un ordre chronologique faussé par des horloges clientes divergentes.
Règle
created_at = heure serveur à la réception (clé du tri). L'heure client de capture est conservée dans l'audit, jamais utilisée pour l'ordre.
Lie
FR-10

05 — La méthode BMad en action

Une revue adversariale a trouvé sept trous

Avant de figer l'architecture, deux relecteurs automatiques l'ont attaquée. Le plus incisif construit des paires d'implémentations toutes deux conformes à chaque règle, mais qui bâtissent quand même de façon incompatible. Voici ce qu'il a débusqué — et qui est déjà corrigé dans la spine.

H1 · dur

Une preuve, ou plusieurs ?

AD-9 disait « le(s) binaire(s) » (pluriel), AD-1 disait « fichier » (singulier). Amina attache 3 photos hors-ligne → au rejeu, l'endpoint composite n'en accepte qu'une → 2 photos perdues silencieusement.

Corrigé : AD-1 accepte désormais files[] 1..N.

H2 · dur

L'heure de capture n'avait pas de canal

AD-5 exige l'heure client dans l'audit d'un dépôt offline différé — mais la requête composite ne déclarait aucun champ pour la porter. Le serveur ne peut enregistrer ce qu'il ne reçoit pas.

Corrigé : champ multipart optionnel clientCapturedAt.

H3 · dur

« 4xx = permanent » était faux

Un 409 de verrou optimiste (deux appareils synchronisent) est transitoire : un retry réussirait. La règle le gelait à tort, indistinguable d'un vrai « déjà résolu ».

Corrigé : AD-10 classe par code applicatif, pas par classe HTTP.

H4 · sécurité

Fenêtre anti-rejeu non spécifiée

Si les nonces sont purgés à 5 min mais le timestamp accepté à ±15 min, une requête rejouée entre les deux passe. Deux implémentations « conformes » divergeaient.

Corrigé : AD-8 fige fenêtre ±5 min, nonce par key-id, rétention ≥ fenêtre.

H5 · moyen

Le plancher comptait-il les pièces du tiers ?

Si le livreur dépose une preuve, l'acheteur peut-il retirer la sienne et laisser le litige « couvert » par la seule pièce d'un tiers ? Ambigu.

Corrigé : AD-4 précise « ≥1 active toutes parties confondues ».

H6 · moyen

10 Mo : 400 ou 413 ?

Selon la limite multipart de Spring, un fichier de 12 Mo rendait un 400 (géré) ou un 413 (hors de l'enveloppe d'erreur standard) — le client offline classait alors des statuts différents.

Corrigé : AD-7 mappe l'exception → 400, enveloppe uniforme.

H7 · convention

Les noms de champs multipart n'étaient pas figés

Un dev nomme le champ file, un autre files[] → 400 au rejeu. Rien dans la spine ne les liait.

Corrigé : une convention fige files[], comment, clientCapturedAt.

La rubrique a aussi noté une dimension oubliée : aucune stratégie de test. Or trois décisions modifient du code déjà couvert. La spine a gagné une section « invariants de test » (étendre EscrowStateMachineTest et HmacSignerTest, tester le rollback atomique d'AD-1).

06 — La stack

Chaque version vérifiée, pas citée de mémoire

L'architecture épingle des versions — et le workflow impose de les vérifier sur le web au moment de l'écriture, jamais de confiance. Deux surprises : Spring Boot 3.x est passé en fin de vie, et le dépôt open-source de MinIO a été archivé.

07 — Ce qu'il faut retenir

Ce que ce POC t'apprend

§

Escrow : la preuve avant l'argent

Un séquestre ne libère les fonds que sur consentement ou arbitrage. Sans preuve traçable et contradictoire, l'arbitre ne peut pas trancher — d'où le litige impossible « à vide ».

◈

L'invariant, pas l'implémentation

Une bonne architecture ne dit pas « écris ce code », elle dit « ne diverge pas ici ». 11 règles suffisent ; le reste appartient au code une fois écrit.

⚔

La revue adversariale gagne son coût

Sept incompatibilités trouvées avant le code — chacune aurait été un bug de production sur le chemin le plus fragile : litige ouvert hors-ligne puis synchronisé.

⟲

Le brownfield se ratifie

Le vrai travail a d'abord été de lire le code existant : conventions d'audit, HMAC, contrôle d'appartenance. On étend, on ne réinvente pas.
